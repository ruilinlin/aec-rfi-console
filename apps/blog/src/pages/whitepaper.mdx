## 1. Problem & Approach

### 1.1 What an RFI is, and what a wrong answer costs

A Request for Information is the formal channel a contractor uses to ask the design team to
resolve an ambiguity in the contract documents: a fastener spacing, a conflicting pair of
clauses, a product substitution. The response becomes part of the contract record and gets
built into the building — so a wrong answer is rework, a claim, or a safety defect. Three
properties follow for any system that drafts RFI responses: every claim must be **cited** to
the governing document, the citation must come from the **current revision**, and when the
documents are silent the only correct output is a structured **"the spec is silent."**

### 1.2 The design principle

The agent is built around one asymmetry: in construction, a deferral costs a day; a wrong
answer costs a rework order. Every layer therefore errs toward abstention. The system never
issues final answers — it drafts responses for a licensed professional to review, and when it
cannot support an answer it returns a `GapReport` naming what was searched and why nothing
governs.

### 1.3 System overview

The stack: Python 3.11, LangGraph for the agent graph, PostgreSQL 16 with pgvector, voyage-3.5
embeddings (1024-dim), claude-sonnet-5 for drafting, FastAPI in front. The pipeline is five
stages — classify → retrieve → cross_check → draft → verify — detailed in section 5. The
corpus is 12 UFGS specification sections (1,524 chunks after the fix in 3.3). Everything
downstream of retrieval exists to turn "found the right text" into "safe to hand to a human."

## 2. Corpus & Provenance

### 2.1 Finding the clean API behind the SPA

UFGS specifications are published on WBDG. The site is a JavaScript SPA, but watching its
network traffic exposed a clean JSON API (`GET /api/documents/{slug}`) with document metadata
and file URLs — no scraping, no HTML parsing. Twelve sections were pinned covering concrete,
roofing, sealants, ceilings, paint, doors, and electrical work, chosen so the benchmark could
ask cross-section questions.

### 2.2 A manifest, not a folder of PDFs

Every corpus file is pinned in a manifest with its source URL and sha256. The downloader is
idempotent: temp-file-then-rename, skip when the hash matches. This sounds like ceremony for
12 files, but the hash shows up twice more in the build: the eval report records the corpus
manifest hash it ran against, and the gap-loop closure notes (section 8) stamp which corpus
state resolved a previously unanswerable question. Provenance is cheap when you add it first.

### 2.3 Schema drift, observed in the wild

The downloader was written against one sample document and selected PDFs by `mimeType`. In
production, WBDG returns `mimeType` (and `fileSize`) as `null` for 11 of 12 documents — the
development sample happened to be the only recently-updated one with populated fields.

<Finding label="Lesson 2.3" title="A populated field is not a schema guarantee">
  Select on the property you actually need (the <code>.pdf</code> extension on
  <code>fileName</code>) and treat every nullable-in-the-wild field as nullable in code.
</Finding>

## 3. Ingest & Section-Aware Chunking

### 3.1 Chunking on the document's own structure

UFGS sections have rigid internal structure: PART headings and dotted clause numbers
(1.5, 3.1.5.2). The chunker splits on those boundaries, so a chunk *is* a clause — which is
what makes a citation like "09 51 00 / 3.1.5" possible. The ablation in section 7 puts a
number on this choice: replacing it with fixed 1,500-character windows costs 41 points of
retrieval recall and 47 points of citation precision.

### 3.2 The documents carry their own revision graph

Each UFGS first page states its revision and the exact revision it supersedes ("UFGS-09 90 00
(August 2026), Superseding ... (February 2021)"). Ingest parses that banner into per-document
metadata and links a supersedes chain automatically — no hand-maintained revision table. The
archive bucket (UFGS_ARCHIVES) supplies each section's most recently superseded revision, which
is what makes the stale-citation metric in section 7 measurable at all.

### 3.3 The bracket that ate the clause numbers

UFGS wraps optional clauses in square brackets, so a heading line can begin with `[3.1.5.2`
or `]1.5`. The heading detector did not match bracket-prefixed lines, and those clauses
silently merged into the previous chunk — a sealant temperature limit was citable only as part
of a "green certifications" clause. The bug surfaced during benchmark construction (section 6),
and the fix was one `lstrip("[]")` before heading detection; the corpus grew from 1,232 to
1,524 chunks. Critically, the fix landed **before** the test set was frozen — frozen gold
labels would have baked the wrong clause numbers in as "correct."

## 4. Hybrid Retrieval

### 4.1 Two signals, fused by rank

Retrieval runs dense (pgvector cosine over voyage-3.5 embeddings) and keyword (PostgreSQL
tsvector) search in parallel and fuses them with Reciprocal Rank Fusion (K=60). Cosine
distances and `ts_rank` scores are incomparable numbers, but ranks always compare — RRF needs
no score calibration, and chunks confirmed by both signals rise.

### 4.2 Section codes are metadata, not text

"09 29 00 fastener spacing" returns zero keyword hits even though the corpus contains section
09 29 00: `plainto_tsquery` ANDs all terms, and a chunk's prose does not contain its own
section number — the code lives in a column. The common claim "BM25 handles exact identifiers"
quietly assumes the identifier appears in the indexed text.

<Finding label="Lesson 4.2" title="Identifiers route, they don't rank">
  The classify stage extracts section codes and applies them as SQL metadata filters. RRF
  degrades gracefully when the keyword ranking comes back empty.
</Finding>

### 5.1 classify

Types the RFI (clarification / conflict / substitution) and extracts section-code hints that
become the retrieval filters of 4.2. Cheap, fast, and the only place free-text turns into
structured routing.

### 5.2 retrieve

The hybrid search of section 4, with the classify node's filters applied.

### 5.3 cross_check

A deterministic walk of the supersedes graph from 3.2: any candidate chunk whose document is
superseded by another document in the corpus is flagged before drafting. No LLM call — it is
a graph lookup that runs in ~8 milliseconds, and section 7 shows it is worth 86 points of
stale-citation rate.

### 5.4 draft

Drafts the answer under a hard rule: it may only cite chunk ids that retrieval actually
provided. Any citation outside that whitelist is dropped, and zero valid citations raises
instead of returning an uncited answer — observed catching the model citing plausible-looking
ids that were never provided.

### 5.5 verify

Two gates. First, every quoted span must match its source chunk **verbatim** — after
whitespace normalization on both sides, because PDF extraction wraps lines mid-sentence and
raw substring checks fail on honest quotes. Second, an LLM review of every claim against its
citation. One plumbing lesson: the verifier needs the same context the drafter had — until
each citation's clause heading was included, the reviewer judged real quotes unresolvable, a
false-abstain class fixed by one line.

<Finding label="Lesson 5.5" title="Verifiers need the drafter's context">
  A verification stage reviewing less context than the stage it audits manufactures false
  negatives. Pass the same section paths, not just the quotes.
</Finding>
